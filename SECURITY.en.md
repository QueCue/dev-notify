# Security Boundaries (Node/npm)

English | [简体中文](SECURITY.md)

The npm package name is `@quecue/dev-notify`, with public source at [QueCue/dev-notify](https://github.com/QueCue/dev-notify). Published versions are authoritative on the npm registry; this document describes the dependency range and security boundaries of 0.2.3, and a source version alone does not establish that an installation package has been published. This project has not completed a security audit or real-machine acceptance on both platforms.

## Communication dependency in current source

Starting with 0.2.3, the standard npm runtime dependency is `@quecue/notify-core` with compatible range `^0.1.0` (stable releases `>=0.1.0 <0.2.0`), with source at [QueCue/notify-core](https://github.com/QueCue/notify-core). Builds do not embed the library or link sibling source; npm installs it automatically. The published `0.2.2` still requires exact `0.1.0`; actual version availability is authoritative on the npm registry. The lockfile still pins the tested `0.1.0` with its official registry source and SHA512 for exact `npm ci` restoration; normal installation permits compatible releases. A permitted version range is not a security guarantee, and neither provenance nor integrity verification constitutes a security audit.

Reusing a dependency does not automatically share credentials or authorization, and a bot's `getUpdates` must still have only one consumer. Upgrade dependencies only from trusted sources; tarball integrity checks in the lockfile do not establish source authenticity or constitute a security audit.

## Credentials and permissions

- Node system credentials use the pinned `@napi-rs/keyring`: Windows Credential Manager / macOS Keychain. Secrets are passed through in-process native interfaces and are not exposed via the shell, subprocess arguments, or plaintext on disk.
- The Node service is `dev-notify.node.credentials.v1`, and each credential uses a random ID. JSON stores only a `keyring` reference and does not enumerate other system entries.
- Environment variables take precedence, and explicitly empty values also override. Neither environment variables nor system credentials can defend against a compromised same-user process; secrets enter Node memory, and it cannot be guaranteed that all copies are securely zeroed.
- Keychain may request system authorization; when storage is locked, permissions are insufficient, or native library loading fails, it reports an explicit error and does not automatically fall back to plaintext. When prebuilt packages are provided, the macOS permission flow still requires separate acceptance.
- The old prototype's `system` references are isolated from Node storage; Node does not read or delete old credentials, and Node references regenerated after re-entering secrets do not need to be handed back to the old prototype for editing.
- Interactive secrets use raw mode hidden input; exceptions, Ctrl+C, and EOF all restore the terminal state; when input cannot be hidden, the wizard refuses to continue and does not fall back to plaintext echo. Native reads may still trigger system dialogs.

## Configuration transactions and cleanup

- Configuration and credentials are not written before final confirmation. After confirmation, a new random entry is created and verified, then JSON is switched, and the old Node entry is deleted on success.
- If the configuration switch fails, the original configuration is retained; only entries created in this attempt are cleaned up, and cleanup failures output only non-sensitive IDs.
- An exclusive `.setup.lock` and content snapshots prevent multiple wizards from overwriting each other; external editors do not honor this lock, so do not manually edit during a save.
- Storage and JSON are not cross-system atomic transactions. Force-kill or power loss may leave locks, temporary files, or orphaned credentials; the program does not proactively scan or delete unknown data.
- `credentials clear` requires interactive confirmation, removes the current reference, and deletes its Node entry; configuration copies sharing the reference are affected, and this is communicated before the operation. Environment variables are not cleared, and deletion failure is explicitly warned.
- POSIX mode cannot replace Windows ACLs; non-sensitive configuration may still expose recipients and local paths.

## Network and application boundaries

- Non-dry-run `send`, the fixed test message **explicitly shown** in the wizard summary confirmation, and Stop / specified Notification events received **after installing the Claude Code integration as part of the summary confirmation** will send notifications.
- Wizard tests use the final configuration after environment overrides; save success and test failure are reported separately and are not shown as fully successful.
- HTTP enables system TLS verification, disallows redirects, uses a 10-second timeout, and caps response size at 1 MiB; underlying URLs, secrets, and raw server response bodies are not printed.
- A network timeout may occur when the server has accepted the request but the client does not know, so exactly-once delivery cannot be promised; to avoid failure, it also does not retry indefinitely.
- Recipient environment variables fully replace the old list and do not implicitly retain old authorization.
- npm installation does not modify application settings or start services. Notification integration and remote replies are two independent layers of authorization; installing hooks alone does not grant input rights. Without authorization, only final replies, specified waiting notifications, and auxiliary metadata are processed.
- After replies are enabled, trusted Telegram private-chat users can submit local Claude input, including Claude commands, so there is a real control risk. It is not an arbitrary shell executor and should not be described as read-only. The bridge does not open a public listener and does not scan transcripts, project content, or version control information; it only reads local Claude session process metadata to locate targets.
- `doctor`, `status`, `paths`, and dry-run do not use the network; local credential reads may trigger system authorization.

## Claude Code integration

- `setup` includes notification hooks by default in the same summary confirmation; before confirmation it shows the sending scope, target configuration, and user-level settings path. `--no-hooks` saves only the notification configuration. It writes to `~/.claude/settings.json` by default and respects an absolute-path `CLAUDE_CONFIG_DIR`. Once enabled, it applies to all projects under that configuration directory; final replies may contain secrets or business-sensitive content, and the program does not automatically redact them. Recipients and sending scope must be confirmed by the user.
- Hooks directly use `last_assistant_message`, do not re-read transcript body text, and do not actively upload thinking processes or tool results; when body text is missing, only an explicit completion notice is sent. Only when the footer template uses `{time}` does a hook read up to the last 2 MiB of the corresponding transcript under the Claude config directory's `projects` folder to extract the `timestamp` of the last `assistant` record; body text is neither read nor sent. The notification footer includes the absolute `cwd` path, session name, and session ID; the session name is read only from the local Claude Code session registry. Input is limited to 8 MiB with a 15-second read timeout; over-limit is rejected, not truncated. Notifications such as permission prompts may also contain sensitive content.
- Generates `command` + `args` in a no-shell-exec form, and paths are not expanded through a shell; a fixed installation uses absolute paths for Node/CLI/configuration, and command arguments contain no secrets. Requires a newer Claude Code supporting this form and `async`; after switching Node or moving the installation directory, reinstall hooks.
- Retains other settings and hooks, deduplicates updates on repeated installation, and removal matches only this tool's markers and argument structure. Old, project-level, or plugin hooks are not automatically deleted and may cause duplicate sending. `status` reflects only local state and does not involve global policy or actual event delivery acceptance; it does not lift disablement, lower permissions, or bypass managed restrictions.
- Writes use a dedicated exclusive lock, before/after snapshots, and atomic replacement with same-directory temporary files; corrupted JSON is rejected. External editors do not honor this lock, so unconditional race elimination is not claimed; force-kill may leave locks or temporary files, and the program does not clean up locks it did not create in the current attempt.
- Notification is asynchronous; Stop and session lifecycle events are synchronous, and state is registered before sending, which may delay the local return. PreToolUse only registers call identity, sends no network notifications, and waits for no answers; PermissionRequest waits in parallel with the native window of a normal interactive terminal, up to 10 minutes, and does not select by default. PostToolUse, PostToolUseFailure, and PermissionDenied are added to process results, for 10 event types in the complete installation. The implementation has been checked against Claude Code 2.1.316; older versions and special hosts may have different parallel paths.
- There is no persistent notification send queue, no automatic resend of entire messages, and no cross-process exactly-once guarantee. Continuing Stop and repeated idle reminders are ignored; on internal errors, only a safe summary is output and the process exits 0, without using exit code 2 to let Claude continue. Only explicitly authorized structured interactions return the corresponding official control JSON.
- Removing hooks, clearing notification credentials, and uninstalling npm are three different operations. Before uninstalling, remove hooks separately; the uninstall script will not modify user settings on its own.

## Replies, interactions, and local state

- `reply setup` separately selects an explicit private-chat chat_id, which must be in the current notification list; group chats, non-private chats, senders whose chat_id does not match, bot messages, and unauthorized notification recipients do not gain input rights. Feishu provides only a Telegram deep link; knowing the link does not constitute authorization. `/chatid` only returns the sender's own private-chat ID and does not grant permission.
- Authorization is bound to the bot fingerprint, random generation, current valid user, and optional permission capability. Switching the token, revoking users, or re-authorizing does not inherit old routing; authorization is re-read before operations and before submission. Revocation cannot withdraw native input that has already started, nor eliminate every race between checking and calling.
- Every authorization read checks the complete hooks bound to the current notification configuration; when lifecycle events are missing, Stop is asynchronous, or user-level hooks are disabled, replies are refused. Normal input also requires actually observing the session's UserPromptSubmit. User-level file checks cannot prove project/managed policy or that a running session has loaded the hooks; confirm in `/hooks`. No promise is made to eliminate all runtime races.
- After each segment is sent successfully, the message ID is saved to the session mapping; mapping failure reports partial failure and does not resend already-sent segments. The session must match PID/birth identifier/TTY; submission is refused on session switch, closure, or a non-unique target. Supported scope is only the Windows native claude console and macOS foreground claude with Ghostty/tmux; no routing guesses are made for WSL/SSH/VS Code terminals.
- Normal replies are only queued while Claude is working and are attempted after Stop; they are canceled on 5-minute expiry, new local input, or a target change. A single reply is at most 4000 Unicode characters; control characters and newlines are stripped and the text is entered once; it is not shell-executed, not truncated, and not automatically split into multiple tasks. Input is refused when the console is shared and multiple claude processes exist; a local user editing or switching terminals at the same time may still race, and native input and UI activity are not atomically mutually exclusive.
- The update offset is persisted before processing; input is registered as pending first, and then the native adapter is called. Force-kill may lose messages, but submitted or unknown-result input is never replayed. Normal reply text is removed before submission; receipt is reported to the original private chat and to configured Feishu only when a matching UserPromptSubmit arrives, and the Feishu confirmation does not include the reply text. "Forwarded", "Received", and "Completed" are reported separately and are never conflated.
- AskUserQuestion uses the original questions + answers and returns them via PermissionRequest decision.updatedInput; the local native UI is retained; single-select, multi-select, and per-question custom input all bypass terminal injection. Claude arbitrates the first complete answer. Each button carries the request/question sequence; expired or old questions do not answer new questions; no default answer is selected on timeout or revocation.
- PreToolUse's tool_use_id and input digest are used for association; PermissionRequest has no such ID and accepts only a unique match, and ambiguity, repeated identical content, missing data, or an already-ended call causes remote handling to be refused. Completion events associate by tool_use_id, without guessing targets from notification order.
- General permission_prompt deduplication is only for notification delivery and grants no input or approval: only when the current session's last call is a question, no other unfinished calls exist, and the structured notification fully succeeded does it override per recipient; Feishu additionally binds to the digest of the current webhook/signature configuration. A completed question may override late reminders within the original interaction validity period; new input and subsequent tool calls do not inherit it. When Notification lacks a precise call identity, the conservative session scope is used for judgment, and precise deduplication across concurrency or turns is not claimed; state abnormalities, delivery failures, or unclear association keep the general reminder.
- Telegram's "Registered" feedback only means the answer has been recorded; effectiveness is confirmed later. The actual answers from PostToolUse are used for content confirmation; when both ends submit the same answer simultaneously, the source cannot be proven. For deny/failure, cancellation, a missing result, or a 10-minute confirmation timeout after returning, when the actual decision cannot be proven, the result is explicitly reported as unknown, and the answer is not replayed. Result receipts are registered before sending; network failure or force-kill may cause non-delivery; there are no unlimited retries and no exactly-once guarantee. After authorization is revoked, no further sends occur. Old options are replaced with processed/timed-out/invalid status; if editing fails, old requests are still rejected.
- After a question ends, request input and answer text are cleared, while message IDs, result receipts, and input digests are retained briefly; when no result is received, they are retained until the confirmation deadline, and actual cleanup is triggered by the active bridge or lifecycle events.
- Tool permissions require an additional opt-in; each click outputs one PermissionRequest allow/deny. Custom text is used only as a denial message; no arbitrary text becomes an approval. It does not persistently write updatedPermissions or change bypass/permission mode; Claude's deny and managed policies still apply. permission_suggestions is not the complete UI list, so not all local buttons are fabricated. MCP forms/URLs and similar are not yet supported for remote answering.
- Questions, options, tool arguments, reply text, and answers may contain sensitive information; after enabling, questions and the corresponding requests are sent to authorized private chats and configured Feishu, with no automatic redaction. Queued text, request input, answers pending return, and session paths are persistently written to dedicated local state; 0600/0700 cannot replace Windows ACL and cannot defend against same-user processes. Logical TTLs do not automatically erase files after power loss.
- The dedicated files are `<config>.reply.json`, `<config>.reply-data/`, and the data directory `reply-bots/`, already added to ignore rules and not in the npm whitelist. Disabling does not delete historical state on its own; to clear it, disable and stop first, then confirm deletion of the dedicated files. The bot token exists only in system credentials, environment variables, or memory and is not written to reply state.
- The bridge does not listen on ports or configure system auto-start. After user authorization, it can be started manually or on demand by hooks; it exits after 24 hours without updates, and also after 5 consecutive polling failures or a 409 conflict. It does not delete webhooks or force-kill old or other instances; cross-machine, cross-implementation bot exclusivity must be ensured by the user. This tool's lock only constrains instances that follow the same local lock directory.
- Stop sends a control request using a random instance identifier and does not kill processes based on an old PID; stop does not revoke authorization, and later hooks may restart the bridge. Use disable for a complete shutdown; native calls cannot be withdrawn once started. Heartbeat/PID are only status snapshots; network connectivity needs separate verification; crash-residual locks require confirming that the process has exited before manual handling, and the program does not automatically seize locks.

## npm and testing

- Runtime has a native credential dependency, with the version and platform optional packages pinned in `package-lock.json`. Keep optional dependencies. There is no postinstall, self-written binary download, or background startup script.
- For the current 0.2.2 source, the npm whitelist includes only this application's compiled CLI JS, README, SECURITY, CHANGELOG, LICENSE and package.json. Library copies, tests, real configuration, logs, ciphertext and dependency tarballs are excluded. Published versions are governed by their actual package contents.
- Third-party native packages carry their own licenses and Rust dependency declarations. Check the supply chain and licenses for releases and dependency upgrades; pinned versions are not equivalent to a completed audit.
- Default tests use fake credentials, temporary directories, and mock system backends/network. `DEV_NOTIFY_NATIVE_TEST=1` explicitly enables Windows native tests, creates only fake entries with random IDs for this run, cleans up afterward, and does not read the user's existing entries.
- npm uninstall does not automatically delete user configuration or credentials. To clean up, first run the interactive cleanup command; uninstall lifecycle scripts will not secretly manipulate the user's system storage.

## Release security and vulnerability reporting

The project is public; see [CHANGELOG.en.md](CHANGELOG.en.md) for release history and the npm registry for published versions. Releases and dependency upgrades still require checking the package name, source ownership, and dependency licenses, and checking source, actual npm packages, and Git history for secrets. Once a key leaks, revoke and rotate it; deleting files cannot undo a leak. This project has not completed a security audit.

There is currently no public security contact email. If GitHub private vulnerability reporting is enabled for the repository, submit privately through its [Security page](https://github.com/QueCue/dev-notify/security). Otherwise, use [Issues](https://github.com/QueCue/dev-notify/issues) only to ask for a private contact method, without publishing vulnerability details, credentials, or sensitive logs.

Windows x64 / Node 24 has had isolated tests and a real CLI fake-network loop; the Windows native input helper class in automation only verifies compilation/layout and does not inject into real Claude sessions. Question-answering acceptance on Claude Code 2.1.316 with real Telegram covers local/remote priority, single-select/multi-select/custom input, competing different answers, and duplicate reminder deduplication; that path does not involve terminal input injection. Tool permission answering on a real machine, macOS terminal input and the system permission flow, other architectures, and the minimum Node version have not been verified, so comprehensive compatibility is not claimed.
