# Security Boundaries (Node/npm)

English | [简体中文](SECURITY.md)

The npm package name is `@quecue/dev-notify`, with public source at [QueCue/dev-notify](https://github.com/QueCue/dev-notify). This document describes current-source security boundaries, including Feishu app mode from 0.3.0 onward. See the [CHANGELOG](CHANGELOG.en.md) for versions and validation scope; publication status is authoritative on the npm registry. This project has not completed a security audit or real-machine acceptance on both platforms.

## Communication dependency in current source

Communication uses the standard npm runtime dependency `@quecue/notify-core`, targeting compatible range `^0.2.1` (stable releases `>=0.2.1 <0.3.0`), with source at [QueCue/notify-core](https://github.com/QueCue/notify-core). Builds do not embed the library or link sibling source; npm installs it automatically. This upgrade does not alter dependency declarations in historical releases. The lockfile pins specific dependency sources and integrity for exact `npm ci` restoration; normal installation permits compatible releases. A permitted version range is not a security guarantee, and neither provenance nor integrity verification constitutes a security audit.

Reusing a dependency does not automatically share credentials or authorization. A Telegram bot's `getUpdates` must have only one consumer; run only one reply bridge per Feishu app. Multiple long-connection consumers split events instead of broadcasting, and local locks cannot constrain other machines or implementations. Upgrade dependencies only from trusted sources; tarball integrity checks in the lockfile do not establish source authenticity or constitute a security audit.

## Credentials and permissions

- Node system credentials use the pinned `@napi-rs/keyring`: Windows Credential Manager / macOS Keychain. Secrets are passed through in-process native interfaces and are not exposed via the shell, subprocess arguments, or plaintext on disk.
- The Node service is `dev-notify.node.credentials.v1`, and each credential uses a random ID. JSON stores only `keyring` references or credential environment variable names, without enumerating other system entries. Plaintext tokens, webhooks, signing secrets, App IDs, and App Secrets are forbidden.
- Feishu App ID/App Secret use hidden input in `setup` and system keyring storage, or are read from `FEISHU_APP_ID`/`FEISHU_APP_SECRET`; `feishu.app_id_env`/`feishu.app_secret_env` can select custom variable names. System credential failures never fall back to plaintext configuration.
- Environment variables take precedence, including explicitly empty values, with no fallback. `FEISHU_OPEN_IDS` completely replaces `feishu.open_ids`; an empty value clears effective recipients instead of appending or retaining old users. Recipients do not gain reply authority from that list alone. Neither environment variables nor system credentials can defend against a compromised same-user process; secrets enter Node memory, and it cannot be guaranteed that all copies are securely zeroed.
- Keychain may request system authorization; when storage is locked, permissions are insufficient, or native library loading fails, it reports an explicit error and does not automatically fall back to plaintext. When prebuilt packages are provided, the macOS permission flow still requires separate acceptance.
- The old prototype's `system` references are isolated from Node storage; Node does not read or delete old credentials, and Node references regenerated after re-entering secrets do not need to be handed back to the old prototype for editing.
- Interactive secrets use raw mode hidden input; exceptions, Ctrl+C, and EOF all restore the terminal state; when input cannot be hidden, the wizard refuses to continue and does not fall back to plaintext echo. Native reads may still trigger system dialogs.

## Configuration transactions and cleanup

- Configuration and credentials are not written before final confirmation. After confirmation, a new random entry is created and verified, then JSON is switched, and the old Node entry is deleted on success.
- If the configuration switch fails, the original configuration is retained; only entries created in this attempt are cleaned up, and cleanup failures output only non-sensitive IDs.
- An exclusive `.setup.lock` and content snapshots prevent multiple wizards from overwriting each other; external editors do not honor this lock, so do not manually edit during a save.
- Storage and JSON are not cross-system atomic transactions. Force-kill or power loss may leave locks, temporary files, or orphaned credentials; the program does not proactively scan or delete unknown data.
- `credentials clear` requires interactive confirmation, removes the current reference, and deletes its Node entry; configuration copies sharing the reference are affected, and this is communicated before the operation. Environment variables are not cleared, and deletion failure is explicitly warned.
- POSIX mode cannot replace Windows ACLs; non-sensitive configuration may still expose recipients and local paths.

## Network and application boundaries

- Non-dry-run `send`, the fixed test message **explicitly shown** in the wizard summary confirmation, and Stop / specified Notification events received **after installing the Claude Code integration as part of the summary confirmation** will send notifications.
- Wizard tests use the final configuration after environment overrides; save success and test failure are reported separately and are not shown as fully successful.
- HTTP enables system TLS verification, disallows redirects, uses a 10-second timeout, and caps response size at 1 MiB; underlying URLs, secrets, and raw server response bodies are not printed. The Feishu app client reuses notify-core's official SDK adapter; these HTTP limits do not establish WebSocket frame-size or processing-time guarantees.
- A network timeout may occur when the server has accepted the request but the client does not know, so exactly-once delivery cannot be promised; to avoid failure, it also does not retry indefinitely.
- Recipient environment variables fully replace the old list and do not implicitly retain old authorization.
- npm installation does not modify application settings or start services. Notification integration and remote replies are two independent layers of authorization; installing hooks alone does not grant input rights. Without authorization, only final replies, specified waiting notifications, and auxiliary metadata are processed.
- After replies are enabled, authorized Telegram private-chat users or Feishu app `open_id` users in the selected channel can submit local Claude input, including Claude commands, so there is a real control risk. It is not an arbitrary shell executor and should not be described as read-only. The bridge does not open a public listener and does not scan transcripts, project content, or version control information; it only reads local Claude session process metadata to locate targets.
- `feishu.mode` defaults to `webhook`, still for one-way notifications. Only a self-built app bot explicitly selected with `app` can receive `im.message.receive_v1` over WebSocket; sending/replying uses HTTP APIs, and card-action callbacks are unsupported. Platform setup requires enabling the bot, choosing long-connection event subscriptions, requesting `im:message:send_as_bot` and `im:message.p2p_msg:readonly`, publishing an app version, and setting its availability scope; see [notify-core setup](https://github.com/QueCue/notify-core/blob/main/README.en.md#feishu-self-built-apps-websocket-reception-and-http-replies). This tool rejects group-chat input; group permissions do not expand its authorization scope. No public endpoint is needed.
- `doctor`, `status`, `paths`, and dry-run do not use the network; local credential reads may trigger system authorization.

## Claude Code integration

- `setup` includes notification hooks by default in the same summary confirmation; before confirmation it shows the sending scope, target configuration, and user-level settings path. `--no-hooks` saves only the notification configuration. It writes to `~/.claude/settings.json` by default and respects an absolute-path `CLAUDE_CONFIG_DIR`. Once enabled, it applies to all projects under that configuration directory; final replies may contain secrets or business-sensitive content, and the program does not automatically redact them. Recipients and sending scope must be confirmed by the user.
- Hooks directly use `last_assistant_message`, do not re-read transcript body text, and do not actively upload thinking processes or tool results; when body text is missing, only an explicit completion notice is sent. Only when the footer template uses `{time}` does a hook read up to the last 2 MiB of the corresponding transcript under the Claude config directory's `projects` folder to extract the `timestamp` of the last `assistant` record; body text is neither read nor sent. The notification footer includes the absolute `cwd` path, session name, and session ID; the session name is read only from the local Claude Code session registry. Input is limited to 8 MiB with a 15-second read timeout; over-limit is rejected, not truncated. Notifications such as permission prompts may also contain sensitive content.
- Generates `command` + `args` in a no-shell-exec form, and paths are not expanded through a shell; a fixed installation uses absolute paths for Node/CLI/configuration, and command arguments contain no secrets. Requires a newer Claude Code supporting this form and `async`; after switching Node or moving the installation directory, reinstall hooks.
- Retains other settings and hooks, deduplicates updates on repeated installation, and removal matches only this tool's markers and argument structure. Old, project-level, or plugin hooks are not automatically deleted and may cause duplicate sending. `status` reflects only local state and does not involve global policy or actual event delivery acceptance; it does not lift disablement, lower permissions, or bypass managed restrictions.
- Writes use a dedicated exclusive lock, before/after snapshots, and atomic replacement with same-directory temporary files; corrupted JSON is rejected. External editors do not honor this lock, so unconditional race elimination is not claimed; force-kill may leave locks or temporary files, and the program does not clean up locks it did not create in the current attempt.
- Notification is asynchronous; Stop and session lifecycle events are synchronous, and state is registered before sending, which may delay the local return. PreToolUse only registers call identity, sends no network notifications, and waits for no answers; PermissionRequest waits in parallel with the native window of a normal interactive terminal, up to 10 minutes, and does not select by default. PostToolUse, PostToolUseFailure, and PermissionDenied are added to process results, for 10 event types in the complete installation. The implementation has been checked against Claude Code 2.1.316; older versions and special hosts may have different parallel paths.
- There is no persistent notification send queue, no automatic resend of entire messages, and no cross-process exactly-once guarantee. Continuing Stop and repeated idle reminders are ignored; on internal errors, only a safe summary is output and the process exits 0, without using exit code 2 to let Claude continue. Only explicitly authorized structured interactions return the corresponding official control JSON.
- Removing hooks, clearing notification credentials, and uninstalling npm are three different operations. Before uninstalling, remove hooks separately; the uninstall script will not modify user settings on its own.

## Replies, interactions, and local state

- From 0.3.2, dynamic Feishu cards explicitly set `config.update_multi: true` to support PATCH updates to the original card; shared updates grant no reply authority. Feishu completion cards initially show Preparing replies. Only after durable message-to-session mapping and bridge verification do they change to Reply enabled. Status is recipient-specific and never grants or broadens authorization; working, verification paused, expired, confirmed closed, and switched states are distinct. The bridge normally checks every 10 seconds, updating at most 8 cards per pass, and reevaluates failed updates after at least 30 seconds. Updates PATCH the original card and never resend a new message or input. Unavailable verification is distinct from confirmed process exit; query failures never imply closure. Reply mappings last at most 24 hours.
- Dynamic status temporarily stores original card bodies, titles, and footers to preserve content while changing status. Each authorization retains at most 256 active cards; bodies may be removed after terminal states, with additional expiry cleanup. This state is not encrypted; never share the full reply directory. Network loss, shutdown, bridge exit, update failure, or revocation can leave stale indicators, so status is neither real-time nor a permanent guarantee. Incoming input still follows the original authorization and session checks. Revocation stops further updates to old cards; cards sent before upgrading are not registered retroactively.

- `reply setup` authorizes replies separately. From 0.4.0, Telegram, Feishu, or both can be selected when available, gathering users and explicitly asking about tool-permission capability independently (default off), then saving once all selected channels are complete without an additional summary confirmation. A blank user list or interrupted setup never saves partial grants. Legacy version 1 single-channel policies remain supported; dual-channel policies use version 2 and must not be downgraded or interpreted by older software. Channels share session queues and interaction state but never inherit users or capability from each other. Telegram accepts only explicitly authorized private-chat chat IDs in the current notification list; group/non-private chats, senders whose chat ID does not match, bots, and unauthorized recipients cannot submit input. `/chatid` returns only the sender's own private-chat ID and grants no authority. The existing Webhook + Telegram deep-link path remains; knowing a link does not constitute authorization.
- Feishu accepts only **p2p user text messages** from explicitly authorized `open_id` values in the current notification list. Group chats, bots, and non-text content are rejected. Continuing a session requires quoting a mapped task completion notification; question answers and permission decisions must quote the corresponding question/permission message. Missing quotes, missing mappings, or mismatched identities/requests never trigger routing guesses. Card visibility grants no input authority, and card-action callbacks are not handled.
- Dual channels use one worker, one owner lease, and shared state, holding both consumer locks in a fixed order and releasing already-acquired locks if the second acquisition fails. Telegram polling and Feishu WS each validate their own authorization view; IDs, recipients, and receipts are channel-namespaced. Ordinary replies share an atomic pending/submission slot, and interactions share the request, question index, and response; duplicate or late answers cannot submit again. The complete current grant is rechecked before replies and submission. Configuration or grant changes rebuild the shared identity and stop the old worker without retaining mappings; invalid credentials never grant another channel's authority. Telegram can remain individually ready during temporary Feishu reconnection, while aggregate readiness requires both channels.
- Authorization is bound to the selected channel's bot/app identity fingerprint, random generation, current valid users, and optional permission capability. Switching channels, app credentials, or the token, revoking users, or re-authorizing does not inherit old routing; authorization is re-read before operations and before submission. Revocation cannot withdraw native input that has already started, nor eliminate every race between checking and calling.
- The Feishu WebSocket inbound callback only validates, deduplicates by event/message identifiers, and durably enqueues, with bounded lock contention designed around the SDK's 3-second callback budget. It never sends network messages, submits input, or waits for answers or permission decisions; blocking disk or credential operations prevent an absolute timing guarantee. The worker then revalidates current authorization and the session epoch, reusing existing queueing, anti-replay, and outcome confirmation. Queueing is neither execution authority nor proof that Claude received input. A failed durable enqueue must not be acknowledged as successfully handled; redelivery must not repeat submitted or unknown-result operations.
- Version 0.2.7 (introduced in `0.2.7-beta.3`) offers a bridge-identity fallback only when every notification `getMe` attempt explicitly fails with connection reset; it neither skips nor adds queries. The valid bot username verified at initialization and the full authorization identity live only in the current owner's lease. Reuse revalidates authorization and session, requiring confirmed process liveness, a fresh heartbeat, ready state, no error, and no stop request for that owner. Older bridges, missing/invalid fields, or authorization mismatch cannot supply a fallback; 401, invalid query results, and other errors do not qualify. Local verification exceptions remain check failures. The username only builds deep links and grants no authority; renaming the bot while the worker runs can stale this initialization snapshot, so it is not a guarantee of a real-time identity lookup. `identityFallback: "bridge"` marks actual use without recording the username in notification diagnostics.
- The read-only notification-button `getMe` lookup retries only on confirmed connection reset (at most 2 times, about 1 s then 3 s, starting with 0.2.8, introduced in `0.2.8-beta.2`; previously once), revalidating authorization, process identity, input tracking, and bridge state before each retry. This does not repeat message sends or input. The send adapter retains only a safe category; a reset after a request is written, or with an unknown outcome, is never resent (see the 0.2.8 entry below for completion-notification reconnects after failed connection setup). `identityRetries` is a local diagnostic count without request bodies or credentials.
- Version 0.2.7 (introduced in `0.2.7-beta.1`) provides a delayed `ECONNRESET` retry allowance for two read-only Telegram initialization queries (one shared retry in 0.2.7; starting with 0.2.8, introduced in `0.2.8-beta.2`, at most 2 per query, about 1 s/3 s, and 3 in total), rechecking authorization and stop state first. It adds no replay to sending messages, consuming updates, or submitting input. Diagnostics preserve only a connection-reset category, not underlying exceptions; request outcomes and the reset source remain uncertain.
- Current source uses fixed `[DN-…]` error codes in the user interface, consistent across languages and describing confirmed failure categories rather than established root causes. Startup parents accept only allowlisted failure keys and stages from their own child's new lease, never arbitrary underlying exceptions or historical worker records as the current cause. For legacy leases, `reply status` displays only a safe fallback code and explicitly labels retained failures. Codes and stages grant no authority and trigger no additional requests or retries.
- Version 0.2.8 (introduced in `0.2.8-beta.0`) adds per-send-unit stages to completion-notification Telegram diagnostics. They contain only plan indexes, recipient order (not a chat ID), part numbers, whether a button was attached, attempt kinds, undici stages, new/reused connection and idle time, address family, numeric HTTP/API codes, and allow-listed error codes; never recipients, bodies, tokens, URLs, IPs, request/response headers, or raw exceptions. The observer subscribes to this process's diagnostics events only during the current hook; the observer itself sends no requests or resends (see the 0.2.8 reconnect entry below for reconnects after failed connection setup). Stages do not prove whether the server received a request and are not a basis for resending.
- Diagnostic prerelease `0.2.7-beta.0` additionally retains the latest notification failure per session and the latest parent/worker bridge failures across successful recovery. These contain only timestamps, stages, elapsed times, safe reasons, and channel counts, with no body, credential, recipient, API URL, or underlying exception. They remain in the dedicated reply directory, are not automatically expired, are not used for replay, and do not establish a current fault.
- Version 0.2.6 also checks accessible Node/CLI hook files and POSIX Node execute permission, without executing those files as a probe. This cannot guarantee Windows execution-policy acceptance or actual loading by a running session. Unavailable session verification marks the session unverified and pauses buttons, input, and permission return without deleting unsubmitted queues; original expiry, new-local-input cancellation, explicit end, and anti-replay rules remain. Already registered submissions are not requeued after a subsequent query failure.
- Every authorization read checks the complete hooks bound to the current notification configuration; when lifecycle events are missing, Stop is asynchronous, or user-level hooks are disabled, replies are refused. Normal input also requires actually observing the session's UserPromptSubmit. User-level file checks cannot prove project/managed policy or that a running session has loaded the hooks; confirm in `/hooks`. No promise is made to eliminate all runtime races.
- In version 0.2.8 (introduced in `0.2.8-beta.1`), completion-notification Telegram sends reconnect the same send unit only when this process observed that the request was created, connection setup failed, and no request headers/body were written and no response was received: at most 2 reconnects per unit (waiting about 1 s, then 3 s) and 4 per notification. Missing diagnostics events, a written request, a received response, HTTP errors, and non-network errors never reconnect. Reconnects do not change content or recipients, do not cross processes, and are not queued persistently; units beyond the eighth are not reconnected. Diagnostics add TCP/TLS sub-stages, a connection-failure category, TCP time, and the attempted address-family sequence (4/6 only, no addresses). Plain CLI `send` is unchanged.
- After each segment is sent successfully, the message ID is saved to the session mapping; mapping failure reports partial failure and does not resend already-sent segments. The session must match PID/birth identifier/TTY; submission is refused on session switch, closure, or a non-unique target. Supported scope is only the Windows native claude console and macOS foreground claude with Ghostty/tmux; no routing guesses are made for WSL/SSH/VS Code terminals.
- Normal replies are only queued while Claude is working and are attempted after Stop; they are canceled on 5-minute expiry, new local input, or a target change. A single reply is at most 4000 Unicode characters; control characters and newlines are stripped and the text is entered once; it is not shell-executed, not truncated, and not automatically split into multiple tasks. Input is refused when the console is shared and multiple claude processes exist; a local user editing or switching terminals at the same time may still race, and native input and UI activity are not atomically mutually exclusive.
- Telegram persists the update offset before processing; Feishu deduplicates and durably enqueues before worker processing. Normal input is durably marked submitted and its text removed before calling the native adapter. Force-kill may lose messages, but submitted or unknown-result input is never replayed. Only a UserPromptSubmit matching the session epoch, text digest, and time window confirms that Claude received input. Receipt is reported to the original authorized private chat; the Telegram reply path retains confirmation to configured Feishu without the reply text. "Queued", "Forwarded", "Received", and "Completed" remain distinct states.
- AskUserQuestion uses the original questions + answers and returns them through `decision.updatedInput.answers` in official PermissionRequest `hookSpecificOutput` control JSON. The local native UI remains; single-select, multi-select, and per-question custom input all bypass terminal injection. Claude arbitrates the first complete answer. Telegram buttons bind the request/question sequence; Feishu requires quoting the corresponding question message and entering one option number, comma-separated multi-select numbers, or custom text. Expired or old questions cannot answer new ones, and timeout or revocation never selects an answer by default.
- PreToolUse's tool_use_id and input digest are used for association; PermissionRequest has no such ID and accepts only a unique match, and ambiguity, repeated identical content, missing data, or an already-ended call causes remote handling to be refused. Completion events associate by tool_use_id, without guessing targets from notification order.
- General permission_prompt deduplication is only for notification delivery and grants no input or approval: only when the current session's last call is a question, no other unfinished calls exist, and the structured notification fully succeeded does it override per recipient; side notifications through a Webhook additionally bind to a digest of the Webhook/signature configuration. Feishu app mode currently keeps the general reminder rather than overriding it based on app-question delivery. A completed question may override late reminders within the original interaction validity period; new input and subsequent tool calls do not inherit it. When Notification lacks a precise call identity, the conservative session scope is used for judgment, and precise deduplication across concurrency or turns is not claimed; state abnormalities, delivery failures, or unclear association keep the general reminder.
- "Registered" feedback on either channel only means the answer has been recorded; effectiveness is confirmed later. The actual answers from PostToolUse are used for content confirmation; when both ends submit the same answer simultaneously, the source cannot be proven. For deny/failure, cancellation, a missing result, or a 10-minute confirmation timeout after returning, when the actual decision cannot be proven, the result is explicitly reported as unknown, and the answer is not replayed. Result receipts are registered before sending; network failure or force-kill may cause non-delivery; there are no unlimited retries and no exactly-once guarantee. After authorization is revoked, no further sends occur. Old Telegram options are replaced with processed/timed-out/invalid status; if editing fails, old requests are still rejected. Old Feishu quoted messages likewise cannot re-execute ended requests.
- After a question ends, request input and answer text are cleared, while message IDs, result receipts, and input digests are retained briefly; when no result is received, they are retained until the confirmation deadline, and actual cleanup is triggered by the active bridge or lifecycle events.
- Tool permissions require an additional opt-in. Only an explicit Telegram choice or `/allow` quoting a Feishu permission message can allow once through official PermissionRequest `hookSpecificOutput` control JSON. `/deny` denies once; `/close` closes remote handling and returns control to the local UI, never approving. Other Feishu text and Telegram custom text are denial messages only; arbitrary text never becomes approval. Questions and permission decisions never use terminal injection. No updatedPermissions are persisted, and bypass/permission mode is not changed; Claude's deny and managed policies still apply. permission_suggestions is not the complete UI list, so not all local buttons are fabricated. MCP forms/URLs and similar are not supported for remote answering.
- Questions, options, tool arguments, reply text, and answers may contain sensitive information. Once enabled, they are sent to authorized private chats in the selected channel; the Telegram reply path retains notifications to configured Feishu. No automatic redaction is provided. Queued text, the Feishu inbound queue, request input, answers pending return, and session paths are persistently written to dedicated local state, **not encrypted storage**. 0600/0700 cannot replace Windows ACLs or defend against same-user processes. Logical TTLs do not automatically erase files after power loss.
- The dedicated files are `<config>.reply.json`, `<config>.reply-data/`, and the data directory `reply-bots/`, already added to ignore rules and not in the npm whitelist. Disabling does not delete historical state on its own; to clear it, disable and stop first, then confirm deletion of the dedicated files. Bot tokens and Feishu App ID/App Secret exist only in system credentials, environment variables, or memory, never as plaintext in reply state; identity digests are not stored credentials.
- The bridge does not listen on public ports or configure system auto-start. After authorization it can start manually or on demand by hooks, using the same `reply start`/`reply status`/`reply stop` commands. The Telegram bridge exits after 24 hours without updates, 5 consecutive polling failures, or a 409 conflict; those polling rules do not describe Feishu WebSocket behavior. It does not delete Telegram webhooks or force-kill old or other instances. Users must ensure exclusive bot/Feishu app consumption across machines and implementations; multiple Feishu consumers split events rather than broadcasting. This tool's lock only constrains instances following the same local lock directory.
- Stop sends a control request using a random instance identifier and does not kill processes based on an old PID; stop does not revoke authorization, and later hooks may restart the bridge. Use disable for a complete shutdown; native calls cannot be withdrawn once started. Version 0.2.4 separates process liveness from heartbeat readiness; an expired heartbeat is not grounds for preemption. A valid bot lock is recovered only when its PID is confirmed absent, with an exclusive recovery gate serializing recovery. Live processes (including reused PIDs), unknown permissions, damaged locks, and leftover recovery gates fail closed; other locks such as state-write locks still require manual handling after exit confirmation. Heartbeat/PID remain status snapshots, not proof of network connectivity.

## npm and testing

- Runtime has a native credential dependency, with the version and platform optional packages pinned in `package-lock.json`. Keep optional dependencies. There is no postinstall, self-written binary download, or background startup script.
- The npm whitelist includes only this application's compiled CLI JS, README, SECURITY, CHANGELOG, LICENSE and package.json. Library copies, tests, real configuration, logs, ciphertext and dependency tarballs are excluded. Published versions are governed by their actual package contents.
- Third-party native packages carry their own licenses and Rust dependency declarations. Check the supply chain and licenses for releases and dependency upgrades; pinned versions are not equivalent to a completed audit.
- Default tests use fake credentials, temporary directories, and mock system backends/network. `DEV_NOTIFY_NATIVE_TEST=1` explicitly enables Windows native tests, creates only fake entries with random IDs for this run, cleans up afterward, and does not read the user's existing entries.
- npm uninstall does not automatically delete user configuration or credentials. To clean up, first run the interactive cleanup command; uninstall lifecycle scripts will not secretly manipulate the user's system storage.

## Release security and vulnerability reporting

The project is public; see [CHANGELOG.en.md](CHANGELOG.en.md) for release history and the npm registry for published versions. Releases and dependency upgrades still require checking the package name, source ownership, and dependency licenses, and checking source, actual npm packages, and Git history for secrets. Once a key leaks, revoke and rotate it; deleting files cannot undo a leak. This project has not completed a security audit.

There is currently no public security contact email. If GitHub private vulnerability reporting is enabled for the repository, submit privately through its [Security page](https://github.com/QueCue/dev-notify/security). Otherwise, use [Issues](https://github.com/QueCue/dev-notify/issues) only to ask for a private contact method, without publishing vulnerability details, credentials, or sensitive logs.

This Feishu app-mode work passed offline regression. On 2026-11-08, the user confirmed a real normal-reply round trip in the current Windows / Node 24.12.0 environment, including notification delivery, quoted input reaching the session, receipt confirmation, and a subsequent completion notification. See the [CHANGELOG](CHANGELOG.en.md) for results and pending validation. Feishu question/tool-permission answering, the macOS app path, and connection-loss/reconnection scenarios still lack field acceptance. Neither one round trip nor existing Telegram/Webhook acceptance establishes comprehensive compatibility or a security guarantee.

Earlier versions on Windows x64 / Node 24 have had isolated tests and a real CLI fake-network loop; the Windows native input helper class in automation only verifies compilation/layout and does not inject into real Claude sessions. Question-answering acceptance on Claude Code 2.1.316 with real Telegram covers local/remote priority, single-select/multi-select/custom input, competing different answers, and duplicate reminder deduplication; that path does not involve terminal input injection. Tool permission answering on a real machine, macOS terminal input and the system permission flow, other architectures, and the minimum Node version have not been verified, so comprehensive compatibility is not claimed.
